## 二、运行环境要求

**最低基础库 2.20.1**（不是随口说的，是可核对的声明）：

| 接口 | 最低基础库 | 低版本怎么办 |
| --- | --- | --- |
| `wx.getWindowInfo` | **2.20.1** | 自动降级到 `wx.getSystemInfoSync`（已废弃但仍可用） |
| `wx.showModal` 的 `editable` | 2.17.1 | 退回不带输入框的弹窗；改奖励只能整条替换 |
| `wx.cloud`（可选能力） | 2.2.3 | 未开通云开发时云层降级为「未连接」，本地功能不受影响 |
| 其余 12 个接口 | ≤ 1.9.x | — |

这份结论写在 [`utils/compat.js`](utils/compat.js) 里：一张 `API_TABLE` 列出用到的 15 个接口
及其最低版本与降级路径，`MIN_BASE_LIB` 由表里最高的 `since` 推出（有断言保证两者一致，
不会各说各话）。尺寸探针 `windowInfo()` 是唯一直接读 `wx` 的地方，低版本自动降级，
两个接口都抛错时返回默认值而不是白屏——这三条路径都有断言。

> `project.config.json` 里的 `libVersion` 只影响开发者工具模拟器，**不代表最低要求**；
> 上传后在「小程序后台 → 设置 → 基础库最低版本」里填 2.20.1。

### 设计令牌的换算规则（不是「尽量取偶」，是两条确定的规则）

README 一开始只写了 `rpx = px × 750 / 390 ≈ px × 1.923`，没说取整怎么办。
`[G]` 段把 41 个令牌逐项核对后，把**实际在用的两条规则**固定下来了：

| 用途 | 规则 | 例子 |
| --- | --- | --- |
| 布局尺度（间距 / 圆角 / 尺寸） | 换算后**向上取偶** | `22px → 42rpx`（42.3）、`30px → 58rpx`（57.7→58） |
| 字号与点击目标 | 换算后**四舍五入**（设计稿给的是整数 px） | `13.5px → 26rpx`、`34px → 65rpx`、`44px → 85rpx` |

核对结果：**17 个颜色令牌逐字一致**、**11 个尺度令牌全部符合规则**、
**5 个维度别名原样保留**、样式里出现的 50 种 rpx 值全部落在规则附近（容差 1rpx）。
`--r-pill: 999rpx` 是特例（本身就是「无穷大」的语义值）。

**允许的偏离只有两类，且都必须能被解释**：

1. **三个字体令牌** —— 平台字体栈替换：
   - `--f-display`：`"Noto Serif SC","Source Han Serif SC","Songti SC","STSong"` →
     `"Songti SC","STSong","Noto Serif SC"`（iOS 自带 Songti SC，比依赖网络字体可控）；
   - `--f-num`：把 `"Noto Serif SC"` 换成 `"Songti SC"`（同上）；
   - `--f-body`：去掉 `system-ui`（小程序不保证支持该关键字），回退仍是 `sans-serif`；

   三个都保留了 `serif` / `sans-serif` 兜底，有断言守着。
2. **三个阴影令牌** —— 观感值的取整差（`18px` 的偏移写成 `34rpx` 而非 `36rpx`）。
   阴影是纯观感，这里只守住**颜色与不透明度一字不改**（那才是设计语义），数值允许 1–2rpx 微调。

### 同步合并：为什么余额不能存一个数字

PRD §9 要求「本地优先 + 可选云同步，冲突用最后写入优先 + 双方可见变更日志」。
家庭共享意味着两台设备（她的手机 / 妈妈的手机）可能各自离线操作再同步，
天真做法（整份状态取「最后写入」）会**丢数据**，而且丢的恰好是最不该丢的。

实现里按数据性质分三类处理（`utils/sync.js`）：

| 类别 | 例子 | 合并方式 |
| --- | --- | --- |
| 只增不改的事件流 | 打卡流水、券、**兑换明细**、修复行动、闪光点 | **取并集按 id 去重** —— 两边各加一条就是两条 |
| 事件派生的标量 | 余额、累计、连续天数、当日得分 | **不合并，重新算** —— 它们本来就是派生量 |
| 真冲突 | 同一天的闪光点、两边都改过规则 | **最后写入优先 + 写进双方可见的变更日志**，不静默覆盖 |

**这轮为此改了一处数据结构**：`spent` 原本是一个数字，两台设备各自离线兑换 20 分会合并成
20（少算一次）。现在兑换记成**只增不改的 `redemptions` 明细**，`spent` 由明细求和派生 ——
合并 = 两条明细取并集，花掉多少永远算得对。老数据在 `load()` 里补一条固定 id 的迁移明细，
余额原样接住。

签名与生效状态**取较严的一方**：只要有一边没签，合并后就不算生效 ——
否则会出现「她这边签了、妈妈那边没签，同步完就生效了」的漏洞（有断言守着）。

### 云安全规则为什么现在就能测
安全规则本来只能配在云控制台、本机测不了，但规则的正确性恰恰是本项目最不能出错的地方
（家长不能删记录、流水只增不改、私密记录不外泄、规则必须双签才生效）。
所以把它写成纯函数 `cloud/authz.js`：`can(actor, collection, action, doc)`，
在 Node 里穷举组合验证；`cloud/database.rules.json` 是它在云侧的等价写法，
`[D]` 段会逐条对拍两边是否表达同一件事。**改任何一边不一致都会被抓出来。**

### 与原型的一致性：移植不是重新设计

小程序是从 [`../prototype/`](../prototype/) 移植来的，所以**原型是设计基线**：
学段日上限、行为项（id / 维度 / 名称 / 分值 / 每日次数）、奖励档位、修复模板、
禁用词库、五个维度，都必须与原型**逐字一致**。`[G]` 段直接读原型源码做对照，
一旦哪边改了忘同步就报错。

这层保护是必要的，因为规则数据的漂移**不会崩**，只会静默改变产品行为。
我实测了三种典型漂移，全部被抓住：

| 注入的漂移 | 被谁抓到 |
| --- | --- |
| 把「整理错题」分值 3 → 4 | `[G]` 行为项对照 |
| 从禁用词库删掉「笨」 | `[G]` 词库逐字对照 **＋** `[C]`「自述命中禁用词库时被拦下」 |
| 小学低段日上限 8 → 9 | `[G]` 学段表对照 **＋** `[C]` 日上限用例（共 4 条） |

注意每一条都是**两层同时响**：`[C]` 段守着「当前实现自洽」，`[G]` 段守着「与设计基线一致」。
两条都绿，才能说「移植是忠实的」。

### 同步的两个核心：并按 id 去重、双签从严

覆盖审计把范围扩到全部 8 个模块后，只揪出两个「被导出但没被测」的函数，
恰好都在 `utils/sync.js` 里 —— 也就是跨设备合并的地基：

- **`unionById`**：按 id 取并集。断言钉住「本机在前、只补远端缺失的、不覆盖本机同 id 记录、
  `added` 是真正新增条数、不就地改写入参、同 id 在远端重复也只补一条」。
- **`mergeSignatures`**：双签的**从严**规则。断言钉住「两边都签才算生效」、
  「一边没签就判未签（宁可不生效，也不能偷偷生效）」、「一边没共建完 `onboarded` 也为 false」、
  「版本取较新、签署时间取较早（保守：规则最多生效到两人都签过的时点）」、
  「不会凭空造出签署时间」。

这两个函数的错误不会崩，而是**悄悄让不该生效的规则生效**或**合并丢数据**，所以值一条条钉。
另外顺带验证了券按 `code` 去重（两台设备可能各自生成同码券），
以及「对端未签时合并结果里的签署状态会被收回」。

### 套件自身的结构完整性

我在给套件加段落时**三次**把相邻段落的注释头替换掉，留下孤立的说明文字（语法检查只抓到一次）。
所以 `[C23]` 段把套件结构也钉住：

- 每个段落注释头后面必须紧跟内容，不能只剩孤立说明文字（做注释深度追踪后判断）；
- `section(...)` 名字互不重复 —— 重复会让统计与定位混乱；
- `ok(...)` 断言名互不重复 —— 重复会让失败报告无法定位。

注入验证：复制一个同名 `section` → 报出重复；复制一个同名断言 → 报出重复。

### 覆盖审计：把「没测过的导出」找出来

我没有靠感觉挑测试目标，而是把 `store` 的 **84 个导出函数**逐个在测试文件里搜引用，
一次就暴露出 **12 个从未被调用的导出**（含 `load` / `replaceState` / `esc` /
`nextReward` / `weekStats` / `dropWeekDraft`，以及 CSV 导出的边界）。
`[C21]` 段就是为它们补的，其中三处是真问题：

1. **`state()` 在读档前是 `null`** —— 真正的读档发生在 `app.js` 的 `onLaunch` 里调
   `store.load()`。我第一版测试直接 `require` 后就用 `state()`，拿到 `null` 才意识到
   这一步必须照真实启动流程走。现在有一条断言守着「`onLaunch` 里确实调了 `load()`」。
2. **存档损坏不能白屏**：坏 JSON、数组、残缺对象三种情况都必须回落到默认状态，不抛错。
3. **CSV 结构不能撑破**：字段里带逗号 / 引号 / 换行时，用自己写的解析器把导出的 CSV
   **解回来**，验证每行列数与表头一致、引号原样还原、合计与 `lifetime()` 相等。

另外 `[C21]` 还钉住了 `esc` 的四个转义（含 `null` → 空串、标签注入）、`monthKey` 的补零、
`nextReward` 的边界（余额超过最高档要返回 `null`）、以及 `replaceState` 之后
**日上限仍然生效**（不能靠替换状态绕过引擎）。

写这一段时我踩了两个测试自身的坑，都记在这里：**重新 `require` 出来的 store 是另一个实例**，
后续段落的状态会分叉；用 `replaceState` 恢复状态时不能顺手 `load()`，否则会被测试存档覆盖。
另外测试里那两句 `PROBE`/自相矛盾的断言（`/^\ufeff日期/` 明明会匹配却断言为 false）也已修掉。

### 撤销的不变式：撤销同时动到四个数

撤销（24 小时内可撤销、不删历史）是最容易被重构改坏的一块 —— 它同时牵动
**今日得分、累计、余额、连续天数**。所以 `[C20]` 段不逐条枚举动作，而是钉住不变式：

> **累计 = 未撤销流水之和**，且 **余额 = 累计 − 已花**。

围绕这条不变式的语义也在断言里定死了：

- 撤销**释放当日额度**：撤销一条 5 分后再记 5+5+3，仍能记到满 12 分
  （临界那条被削减成 2 分并标 `overflow: 1`）；
- 撤销**不删流水**，只打 `reversed` 标记（历史必须留着）；
- 撤销**不计入累计**（累计 = 12，不是 17）；
- 连续天数只看「那天有没有未撤销的记录」：撤销昨天那条 → 连续从 2 回落到 1；
- 同一条不能撤销两次；不存在的 uid 被拒且理由明确；
- **撤销打卡不回收已发出的券**（券一旦发出不可撤回，与 PRD §1.4 红线 4 同理）；
- 撤销后余额可以为负（花掉的分仍要算），但「累计 − 已花」必须仍然自洽；余额为负时不能再兑换。

注入验证：① `lifetime` 忘记排除已撤销的流水 → **4 条**断言失败，不变式直接报
`{"lifetime":17,"sumActive":12,"ok":false}`；② 幂等判断失效 → 「重复撤销被拒」失败；
③ 撤销时把整条从流水里删掉 → **5 条**失败（含「撤销率与私密率算得出来」）。

### 日期地基：跨月、闰年与时区

留存（D7/D30）、连续天数、周窗口、券有效期、徽章达成日全靠几个日期函数。
它们错了不会崩，只会**算错日子** —— 最难发现的一类。所以 `[C]` 段把这一层单独钉住：

- `shiftDay` 在 **±400 天**范围内严格递增、格式统一，`shiftDay(0)` 就是今天；
- `daysInMonth` 覆盖 4/6/9/11 月与 12 月，**闰年 2 月 = 29 天、2100 年不是闰年**；
- `dateKey` 跨 12 个月逐日抽查，确认按**本地时间**格式化、没有时区偏移；
- 跨月 / 跨年 / 闰日推算（`01-31 +1`、`02-28 +1`、`2024-02-28 +1`、`12-31 +1`、回退一个月）；
- 一周窗口是 7 个互不相同的日期，以今天开头、六天前结尾；
- **徽章达成日的时区回归**：连签发生在 6~12 天前时，达成日必须是「六天前」而不是今天。

注入验证：把 `daysInMonth` 换成不含闰年规则的近似式 → 报「29/28/**29**」（2100 年被当成闰年）；
把 `firstStreak7Date` 退回 `new Date('2026-10-04T12:00:00')` 这种 ISO 字符串写法
（真 bug 的原形，按 UTC 解析，东八区偏移一天）→ 达成日断言立刻失败。

> 顺带一个教训：我第一次注入用的是 `new Date(Date.UTC(y, m, d))`，**没被抓到** ——
> 因为 UTC 午夜在东八区是当天 08:00，本地访问器读出来还是同一天。
> 也就是说**注入必须复现真 bug 的形式**，随便找个「看起来像错」的写法不算验证。

### 惊喜卡的「每周最多 1 次」曾经是个洞

PRD §4 M6 规定连续 7 天达成后「每周最多 1 次」自选。我最初把这条写成
`canDraw = 连续 ≥ 7 天 && !S.surpriseAt` —— 看起来没问题，但 `resetWeek()`（周报上的
「下周继续」）会把 `surpriseAt` 一起清掉，于是她**走完周复盘点一下就又能在同一周领一张**。

实测复现：连签 47 天的状态下，领第 1 张 → 走周复盘 → 「下周继续」→ 第 2 张也领到了，
券包里出现 2 张惊喜卡。

修法是把「领过没有」从布尔值换成**记录领取窗口**：

- 领卡时写入 `surpriseClaim = { at, start, end }`（start/end 是当时的滚动 7 天窗口）；
- 判定改成「今天的窗口与已领窗口有交集 → 不能再领」，与 `weekStats()` 的窗口同口径；
- `resetWeek()` **不再清**这个凭据；窗口自然滚过去之后资格自动恢复（不需要手动重置）；
- 被拒时提示具体日期（「本次窗口已经领过了，2026-10-11 之后可以再挑」），不再是一句模糊说法。

顺带补上迁移路径：只有旧字段 `surpriseAt` 的老存档会退化成「7 天内算本窗口」——
否则老用户会被当成「窗口外」而白送一张（这个洞我也实测确认过）。

### 红线声明：不能只靠「扫描没问题」，要逐个点名

「不做扣分」「不做排行榜」「不做家长监视面板」这类约束有个特点：**中文里到处是它们的
否定式说法**（「没做到不用扣分」「这里没有排名」），所以任何朴素的「扫描违规」都不可靠。

换个思路：把**当时的全部出现位置**钉下来（[`redline-declaration.json`](redline-declaration.json)），
每个概念给出理由、总数、涉及文件与每文件次数。任何新增/删除都会让计数变化 → 测试报错 →
改的人必须确认它属于哪一类：**否定式说明 / 拦截守卫 / 用户可见文案**。

| 概念 | 出现处 | 涉及文件 | 说明 |
| --- | --- | --- | --- |
| 负分 | 9 | 5 | 全是否定式说明与 guard 名 |
| 扣分 | 14 | 10 | 「不扣分」文案 + `addPoints` 拒绝非正数 |
| 排名 | 22 | 5 | 否认文案与红线词表，无排行逻辑 |
| 比较 | 23 | 6 | 同上 + templates 学段语气「不比较」 |
| 监视 / 查岗 | 2 / 1 | 1 / 1 | 只在红线词表里 |
| 删除 | 31 | 11 | 只有「她自己的彻底删除」与「明确声明不能删」两类 |
| 撤回 | 10 | 7 | 声明文案 + 「store 不提供该接口」 |

声明文件**自身不参与扫描**（否则它提到「排名/比较」会把计数搅乱，形成自我引用的死循环 ——
这个坑我第一次就踩了）。注入验证：新增一处「负分」→ 报「声明 9 处/5 文件，实际 10 处/6 文件」；
「排名」「监视」同样被抓到。

写这份声明时我又被自己的规则拦了一次：三条理由我写了「同上」，被「理由必须够长」的断言
顶回来 —— 和文案豁免那次是同一个毛病，已改成独立理由。

### 文案红线：豁免必须带理由，而且理由会被验证

`[F]` 段管的是「写死的 UI 文案本身干不干净」，与 `[C]` 段（验证文案引擎会拦截）分工不同。
难点在于朴素子串扫描会大量误报 —— 产品里到处是**在否认羞辱**的句子：

> 空白 = 那天在休息，**不是失败**
> 这里**没有排名**，也**没有**「别人家的孩子」

所以规则有三层：

1. **否定语境**：命中词前面 6 个字内出现否定词（不是 / 没有 / 不排 / 不比…）就不算违规；
2. **豁免表**：`copy-redlines.json` 里的每条豁免都必须写 `reason` 与 `evidence`；
3. **豁免表自检**：测试逐条验证 —— 理由够不够长、`evidence` 字符串是否**仍然真的在对应文件里**、
   以及这条豁免是否**真的还被现在的文案命中**。任何一条不成立就报错。

也就是说豁免表不能当垃圾桶用：文案改了、证据没了、或者豁免成了无用的残留，测试都会顶回来。
实测 8 条豁免全部有理由且证据成立，扫描覆盖到全部面向孩子的静态文案。

**注入验证**（每条改完立即还原）：塞进「你太粗心了」→ 抓到「粗心」；塞进「你看看人家」→ 抓到比较词；
塞进「我会盯着你」→ 抓到监视语气；而塞进否定句「不是失败」→ **正确放行**。

### 模板表达式检查：170 条表达式真的求值一遍

`[E]` 段还会把每个页面 `onLoad()` 之后的**真实数据**喂进模板，
逐条求值 WXML 里 `{{...}}` 的表达式（170 条，全部求值、0 条跳过），
抓住两类渲染期问题：

- **抛错** —— 例如在 `undefined` 上继续取属性（`report.bonusDetail.x.y`）；
- **算出 NaN** —— 数值表达式因为字段缺失而变成 `NaN`，界面上会显示成「NaN」。

**这个检查的边界要说清楚**：它抓的是「会抛错 / 会出 NaN」，**不是语义错误**。
例如把 `report.bonusDetail.week50 ? '✓' : '○'` 改成 `report.bonusDetail.week50.deeper ? …`，
在 JS 里读布尔值的属性只会得到 `undefined`、**不会抛错**，所以检查器保持沉默 —— 这是刻意的：
它不做类型推断，只保证「页面不会因为模板表达式而崩」。语义对不对要靠 `[C]` 段那些
在真实引擎上跑的断言。

写这个检查器时我自己踩了两次坑，都值得记下来：

1. 第一版靠**标签正则**维护 `wx:for` 作用域栈，结果漏掉了 growth 页那个**跨行书写**的
   `<view wx:for="{{timeline}}" ...>` 循环，导致里面所有 `item.*` 被误报成「item is not defined」。
   改成**直接搜 `wx:for`** 再向两边扩到所属标签、并配对求闭合范围，才准；
2. 作用域必须同时包含**页面 data 的顶层字段**与循环别名，而且别名要先于本标签的属性求值
   （WXML 里 `wx:for` 的作用域包含元素自身）。

### 页面接线：把「跑代码」和「读代码」分开

静态检查（正则扫源码）有一类事永远查不到：**页面有没有真的调用对 store 接口**。
所以 `[E]` 段搭了一个最小页面运行时——把 `Page` / `getApp` / `wx` 挂成桩，
然后 **require 真实的页面模块**（不是 eval 源码，否则会丢掉模块级的 `const app`），
再驱动它：`onLoad()` 渲染、模拟点击、走完 5 步向导，断言 store 真的被写了、
页面数据真的跟着变了。

这一层立刻抓到一个**真 bug**：`pages/onboarding/index.js` 调了 `store.stageOf(s.stage)`，
但 `store.js` 从没导出过 `stageOf` —— 也就是**首启共建页的 `render()` 一跑就抛
`TypeError: store.stageOf is not a function`**，整个闸门页根本打不开。
它躲过了此前所有检查：`vm.Script` 只编译不执行、正则只比字符串。
修法是补上导出（顺带把 `templateOf` / `dimOf` 一起导出），并加了一条通用断言：
**页面/组件里出现的每一个 `store.xxx` 都必须真的存在于导出表里**。

### 模板字段检查：抓「只在真机上才看得见」的那类 bug

写错一个字段名，小程序不会报错，界面只是**空白**——开发者工具也只在控制台给条警告。
所以在 `[A]` 段加了一个检查：把每个页面 WXML 里 `{{...}}` 的**根标识符**抓出来
（扣掉 `wx:for` 的作用域别名，以及 `对象.属性` 里的属性名），
要求每个名字都在页面的 `data` **或** 某个 `setData({...})` 里出现过。

这个检查一上线就抓到两个真 bug（不是误报）：

- `pages/onboarding` 的模板用 `{{scores}}` 作 `picker` 的 `range`，但页面从没赋过这个字段
  → **分值选择器的候选是空的**，她在共建页根本挑不了分值；
- 同一个页面的根节点用 `class="page-root stage-{{stage}}"`，但 `stage` 也没赋过
  → 首屏主题类拼成了 `stage-`，学段主题不生效。

两个都属于「不报错、但功能不可用」。另外这个检查自己也修了三次才准：
先是抽 `data` 键时把嵌套键也抽了进来（`week50` 被当成顶层键，掩盖真正的缺失），
再是 CRLF 让行首判定失效，最后是 `setData({ amend: s.amend })` 这种嵌套对象
让「匹配到第一个 `}` 就结束」的偷懒写法漏掉了整个实参——改成数括号配对才对。

### 得分环为什么能被 Node 测到

得分环是唯一无法靠静态检查确认的功能，所以 `_smoke_s1.js` 的 `[A2]` 段搭了一个最小
小程序运行时桩（`Component` / `wx.createSelectorQuery` / 记录型 `ctx`），把
`components/ring-progress/index.js` 真实跑一遍，然后断言：

- `score=3 / cap=12` → 起始角正好 `-π/2`、扫过正好 `π/2`；
- `score=6 / cap=8` → 扫过 `3/4` 圈（日上限换学段后角度跟着变）；
- `score=0` → 只画底环不画进度环；`score > cap` → 按上限收敛，不会画过头；
- 渐变端点是原型的 `#F0A868 → #C4662C`，线宽 9px，`dpr=3` 时位图 336×336；
- 拿不到 canvas 节点（老基础库）时不抛错、`ready` 保持 false、显示 CSS 兜底环。

## 四、三条硬约束在这里怎么落地

| 约束 | 实现位置 | 回归断言 |
| --- | --- | --- |
| **只加分** | `store.addPoints()` 是唯一写入口，`!(points > 0)` 直接拒绝并返回「系统里没有扣分」 | 负数 / 0 分被拒且不落流水；全历史流水无负分 |
| **日上限随学段** | `capNow()` 取自当前学段模板；`addPoints` 里 `grant = min(points, cap - used)`，**在引擎层**强制 | 初中 12 / 低段 8 / 高段 10 / 高中 12；入账合计从不越过上限；满额后加分被拒且文案正确 |
| **必改 3 项 + 双签** | `amend.{point,item,reward}` 三处计数；`finishBuild()` 未满 3 处返回 `{ok:false, reason:'还差 N 处'}`；`parentAgree()` 在家长没签前 `isRuleActive()` 为 false | 0/1/2 处时调用被拒；3 处才生成 `ruleVersion`；孩子签完但家长没签 → 规则未生效；任何一处再改 → 签字作废；换学段 → 两者一起清零 |

### 「必改 3 项」的四层执行链（不只是按钮置灰）

只让按钮 `disabled` 是拦不住的（返回键、分享链接直接进某个 tab 都能绕开）。所以：

1. **冷启动**：`app.gateOnboarding()` 在首页 `onLoad` 里调用，按状态分流 ——
   孩子没改完 → `pages/onboarding`；改完了等家长 → `pages/parent`。用 `wx.reLaunch`
   （清空页面栈，返回键回不去）；
2. **日常兜底**：`utils/guard.js` 的 `requireOnboarded()` 挂在**每个 tab 页的 `onShow`**
   第一行。这条同时覆盖「切换学段」——`applyStage()` 会把 `onboarded` 与家长签署一起撤掉；
3. **家长端特例**：家长端把自己路由传给闸门（`requireOnboarded('pages/parent/index')`），
   **永远放行**。否则会死锁：她改完提案全站被拦，家长却进不来签字。它自己用
   `ruleSignature().active` 决定显示签署屏还是完整家长端；
4. **引擎防线**：`finishBuild()` / `parentAgree()` 各自校验前置条件，
   前端跳转只是体验。

页面在跳转前用 `wx:if="{{onboarded}}"` 包住根节点，避免闪出内容。
共建页自己**不**调用闸门（否则会自己跳自己），跳转去重也有测试守着。

### 规则双签：单方修改不生效

PRD §3 表格写得很明确：**规则变更需孩子 + 家长双签，单方修改进入待生效**。
所以本工程把「改满 3 处」和「规则生效」拆成两件事：

```
孩子改满 3 处 → finishBuild() → onboarded = true，但 isRuleActive() 仍为 false（待生效）
家长点「我按你的版本来」→ parentAgree() → isRuleActive() = true，记下生效日期
```

三个关键点（都有断言守着）：

- **任何一处规则改动都作废上一轮签字**（`setItemPoints` / `addItem` / `removeItem` /
  `setRewardTitle` 都调 `revokeSignature()`）。只在 `finishBuild` 里清是不够的 ——
  否则「签完字之后再改一条分值」就会带着旧签字继续生效，等于绕过双签；
- **换学段**同时撤掉 `onboarded` 与家长签署，她必然重走一次共建 + 重签；
- **签署是可见的双向留痕**：家长签署前会看到「她改了哪 3 处」的清单（知道自己同意了什么），
  孩子那边在「我的」页看到「妈妈已确认 · 生效日期 ×××」。

配套红线也有静态断言守着：`store` 不暴露任何删除券 / 撤回券 / 删除流水的接口
（家长端因此没有撤回能力），修复行动不产生任何分数变动，禁用词库（≥ 10 个词）不可缩减，
肯定句式强制「我看到你……这说明你……」。

## 五、移植时做的三处必要改动（都不是设计改动）

1. **`:root` → `page{}`**：小程序没有 `:root`，CSS 变量改挂在 `page` 上（颜色令牌一个没改）。
2. **`[data-stage]` → `.stage-p12` / `.stage-high`**：WXML 是数据驱动，没有属性选择器等价物，
   学段主题改成在页面根节点拼 class，与移植指南 §二给的写法一致。
3. **删掉舞台层与不受支持的能力**：`.rail` / `.phone` 评审外壳、`color-mix()`（改预计算 rgba）、
   `backdrop-filter`（改不透明背景）、`aspect-ratio`（改固定高度）、媒体查询、`@media print`
   （打印改走服务端 PDF，见移植指南 §三）。

### 得分环的单位陷阱（S3 踩到的）

canvas 是**原生组件，只认 px 不认 rpx**，所以它不能像其它元素一样直接用 rpx 写尺寸。
本工程的做法是：设计稿 112px 的环，在页面里按 `当前 px = 112 × 视口宽 / 750` 折算出本机
应显示的 px（390 宽视口 → 58px），再传给组件的 `size` 属性；组件内部一律按 px 计算并
乘 `dpr` 设位图尺寸。这样环在任何屏幕密度下都不发虚，尺寸也与原型 1:1。

## 五、验证的边界（重要）

本工程的 300+ 项断言**全部跑在 Node 里**。它们能证明引擎行为、配置完整性、
移植合规、Canvas 绘制参数、以及部分结构问题；但有明确的边界，不要把它当成真机通过：

**能证明的**

| 类别 | 怎么证明的 |
| --- | --- |
| 三条硬约束与全部计分行为 | 在真实 `utils/store.js` 上跑（唯一写入口、日上限、必改 3 项、双签、隐私过滤） |
| 得分环的几何与颜色 | 最小运行时桩执行 `Component` 的绘制路径，断言角度 / 渐变 / dpr / 老基础库兜底 |
| 配置完整性 | `app.json` / 各页 `.json` / `project.config.json` 都是合法 JSON，页面四件套齐全，图标存在且 81×81 |
| 移植合规 | 去注释后扫描不受支持的写法（`innerHTML` / `color-mix` / `:root` / `@media` / `px` 布局值 / DOM API） |
| 结构性错误 | 全部 JS 用 `vm.Script` 编译；WXML 标签配对；`bind*` / `catch*` 的处理函数在页面 JS 里都存在；**事件名合法、形参能接住事件对象、每个 wx:for 都有 wx:key**；**WXML 引用的每个字段都在页面里赋过值**（data 或 setData） |
| 包体积 | 按主包 2MB 上限估算（当前约 150 KB 级） |

### 隐私标记：在引擎层过滤，不靠页面自觉

PRD §2.1 把她定义为**数据主人**，§4 M4 允许她设「仅自己可见」，家长端的能力边界也写着
「不可查看被标『仅自己可见』的内容」。这一条如果只在页面上写 `filter`，任何一处漏写就是隐私泄露，
所以本工程把它放在引擎层：

- `setEntryPrivate(uid, isPrivate?)` 打标记（不传第二参是切换语义），记 `privateAt`；
- **`visibleToParent()` 是家长端唯一允许的数据来源**，它直接剔除带 `private` 的条目；
- 家长端页面里**不出现任何 `log` 字样**（有断言逐文件扫描守着），要统计「有几条被收起来」
  也必须走 `hiddenCount()` —— 只报数、不报内容；
- 她自己在成长页有开关（「只给自己看 / 让家长看到」），私密条目标记出来；
- **标私密不改分**：她自己该得的分数照旧计入日上限与累计，隐私只影响可见性；
- 她自己的导出（一周一页）**包含**私密条目并在纸面上标注 —— 家长端的不可见不适用于她自己的档案。

### 打印 / 导出：现在就能用，接了后端不用改内容

移植指南 §三要求打印走服务端 PDF（`wx.downloadFile` + `wx.openDocument`），那需要一个后端接口。
本工程先把同一份内容在本地生成好、用**剪贴板**交付（能贴进备忘录、微信、打印店的文档），
`buildWeekPage()` 同时返回 `pdfPayload` —— 后端就绪后直接 POST 这个对象即可，内容不用重写。

「一周一页」包含：周范围与得分、有记录天数与连续记录、累计与余额、周结算奖励及其构成、
维度分布、这一周做到的事（带那句具体反馈）、她手写的闪光点、周复盘的三件事 / 留下的习惯 /
下周那件小事 / 新任务、留给家长手写的一句话栏位、双签栏（版本 + 生效日期 + 签名线）。

### 周奖励与日上限的取舍（S3 必须做的决定）

PRD 里有两条硬要求在这里冲突：

- §5 表格：**日上限 12 分（引擎级不可绕过）**；
- §4 M5 + 附录 A.2：周复盘提交后**自动入账**周达标 +10、连续 7 天 +10、主动挑战 +5（固定值）。

如果周奖励直接走 `addPoints`，那么她今天恰好打满 12 分时（实测很容易复现：当天再得 2 分即触顶），
承诺的 +25 只会到账 +2 —— 上限守住了，PRD 承诺的结算却没兑现。本工程的处理是：

1. 周奖励走独立的 `addWeeklyPoints`，它**不占当日打卡上限**，因为周结算是独立的结算事件而非当天打卡；
2. 但它仍然只加分（非正数拒绝）、走同一套流水结构与文案、同样不可删除，账上带 `weekly: true` 标记；
3. 当日得分仍严格 `≤ 上限`（`dayScore` 只统计打卡流水），所以「引擎级不可绕过」在**当日计分**这件事上完全成立；
4. 结算幂等：同一周（按 `rangeStart` 判定）只结算一次 —— 没有这道闸，结算后再走一遍向导会再发一次奖励。

> 这一条是与 PRD 措辞有出入的地方，已在此明写；若产品坚持「周奖励也计入当日 12 分上限」，
> 只需把 `finishWeek()` 里的 `addWeeklyPoints` 换回 `addPoints`，并接受奖励可能被上限截断。

> `widget` 图标、字体子集化（移植指南 §七）与隐私保护指引配置同样属于提审前必做项。
